# Genesis long-term memory

English | [中文](memory.zh.md)

## Enable

Genesis's optional `memory` configuration enables semantic recall and independent post-turn memory updates. The decision and writer receive bounded evidence from the completed turn, never another Session's transcript. The Web life overlay defaults to TypeSafe Jev for decisions; the memory-only overlay retains registered Harness LLM routes. See the [official System One API](https://api.typesafe.ai/redoc) for the Jev request and response protocol.

Set `GENESIS_EMBEDDING_URL` to the full OpenAI-compatible `/embeddings` endpoint, `GENESIS_EMBEDDING_MODEL` to its model identifier, `GENESIS_EMBEDDING_DIMENSIONS` to its vector length and `GENESIS_EMBEDDING_API_KEY` to its credential in the launching environment. Do not put credentials in patches or Git. Apply the supplied memory overlay after the Genesis overlay:

```sh
pnpm dsh --profile headless --patch packages/experimental/genesis/cordis.patch.yml --patch packages/experimental/genesis/cordis.memory.patch.yml --dump-config
```

The dump checks composition without making model calls. Remove `--dump-config` and supply a task to converse after configuring the endpoints. The sample selects `deepseek-official/deepseek-v4-flash` for both auxiliary roles; change `memory.decisionProvider`, `decisionModel`, `writerProvider` and `writerModel` to select other registered routes. A keyless local embedding server can omit `embeddingKeyEnv` in a custom patch. Omitting the entire `memory` block retains the earlier lexical/manual memory behavior.

## Web configuration

With the Genesis browser companion and memory or life overlay enabled, open Settings → Knowledge Base. Configure the decision model, independent memory update model and embedding service there. Jev uses a full `/v1/systemone` URL, model and yes-probability threshold; the writer uses an existing Harness provider/account or a dedicated OpenAI-compatible `/chat/completions` URL and model. Save keys separately in password fields through the Harness credential store. Model checks prepare registered routes or send the configured credential to `/models` and verify the selected model; they do not run inference or prove access through a public catalog. System One checks accept TypeSafe `models[].name` and OpenRouter `data[].id` catalogs; OpenRouter requests include `output_modalities=decisions`. Catalog responses use `modelCatalogChars` (default 4,000,000 characters), independently of `memory.outputChars`, which continues to bound inference responses. Embedding testing makes one actual request and validates its dimensions. Each request sends one text and requires exactly one finite, nonzero vector. The single result may omit `index`, as observed with Gemini’s OpenAI-compatible endpoint; an explicit index must be numeric `0`. Life information owns identity, naming and growth.

Saved GUI model and embedding preferences override deployment values for subsequent operations and survive restart under the same storage root. Each review captures one pair of model routes and one embedding space. A changed endpoint, model or dimension rebuilds incompatible recalled vectors. Drafts and previous search results survive failures. Settings errors display the affected operation and its specific diagnostic; password values and provider response bodies are excluded. Concurrent saves are refused by revision; refresh and Reload configuration before retrying. Removing a stored key may reveal an environment fallback; disable authentication for a keyless service.

Nonsecret GUI preferences use the version-1 `genesis_embedding_settings` and `genesis_model_settings` Storage Domains under the life writer lease. They remain separate from the life snapshot and its JSON backup; include both domains and the credential store in deployment backups. Invalid or incompatible preference storage fails visibly. An uncertain preference write stops dependent operations until verified reload; it never replaces life identity.

## Participant identity

Set your name and identity in Settings → Memories → Your identity. The life name and this explicit profile accompany bounded memory inference and character context. New summaries use those names instead of generic participant roles. Saving identity also relabels current legacy memories, habit cues/responses and experience topics; the model selects existing role spans and the Host substitutes the supplied names without allowing factual rewrites. Technical terms, third parties and protocol attribution enums retain their meaning. All batches and refreshed embeddings must succeed before the profile and replacements commit together; `memory.identityRewriteLimit` bounds the complete set. Conflicts or inference failures retain both the previous profile and memories. Historical versions and Session logs remain evidence of their original wording.

## Memory time

Stored prose distinguishes ordinary event time from dates worth remembering exactly. `{{time:YYYY-MM-DD}}`, `{{time:YYYY-Www}}` (ISO Monday week), `{{time:YYYY-MM}}` and `{{time:YYYY}}` describe ordinary experiences and render relatively. `{{date:YYYY-MM-DD}}` preserves an explicitly evidenced birthday, anniversary, appointment, deadline or requested exact date; the other calendar precisions also support `date`. Annual birthdays or anniversaries with no known year use `{{date:--MM-DD}}`, without inventing a year. The writer selects exact retention from the cited facts, not from a record's storage timestamp. Explicit times of day can remain beside an anchor.

Writers receive source-message timestamps and a clock in the configured IANA `timeZone` (host zone by default). Relative statements refer to their cited message time, never an unrelated later review. Selected-memory organization makes one additional writer call to review complete draft sentences against the same evidence before embedding. That semantic pass can annotate genuine temporal expressions, preserve exact dates, repair invalid markup or explicitly mark unknown time; ordinary words, names, ages and version numbers stay intact. The Host accepts only complete draft IDs and their reviewed prose, retaining source references, categories and scores from the original draft. Both calls share the captured model route, input/output bounds and operation deadline, and both are logged. A failed or incomplete review retains the selected records. Known time/date anchors survive synthesis even when omitted by the model. Synthesis creation time does not date its original experience.

Character-facing recall, associated cues and prompt memories retain `date` anchors as precise calendar dates while rendering `time` anchors and recording/experience/history timestamps relatively. Ordinary time prefers today/yesterday/the day before yesterday, then this/last week, this/last month, elapsed months, half a year, last year and elapsed years at the stored precision. Relative labels describe the retrieval moment; retrieve again when revisiting an old tool result later. Management views and auxiliary maintenance keep internal anchors. The Host validates and renders only complete explicit time/date markers; it never interprets or rewrites substrings in ordinary prose. Manual entries and unmarked legacy prose remain unchanged, including ages, version numbers and ambiguous dates. Organizing those records lets the model interpret their time meaning from the original evidence. Explicit `date` markers preserve important exact dates, while `time` markers render relatively.

## Recall and updates

The current Session conversation is short-term memory. Declarative long-term memory stores episodes, statements and self knowledge; a small related subset can enter the logged working context. The AI actively calls `genesis_recall` with a nonempty query using approximate topics or related words; Life mode exposes this innate tool before any explicit learning. The knowledge base embeds queries and records, combines lexical matches in content, historical versions and topics with cosine similarity and returns complete records within the query and result budgets. Non-declarative memory stores a small set of durable habits or persona guidance and enters the logged prompt as attributed, untrusted candidate data. Missing historical kinds classify procedural entries as non-declarative and other categories as declarative.

Auxiliary model inputs and completed responses are logged before memory publication: registered LLM routes use ignorable `plugin:genesis/memory-call` records; dedicated HTTP routes use `plugin:genesis/model-http` records with the exact nonsecret body. Authorization headers are excluded. These records stay in their source Session, never enter chat context and never drive recovery. Readers unfamiliar with Genesis retain and skip them.

After each completed user/assistant turn, one decision call determines whether to update memory. Jev sends the conversation as `state` with a named `noul` question and compares `answers.remember.noul` with the configured threshold. A no-update decision makes no writer or review-time embedding call; pre-reply association has its own bounded embedding work. A positive decision invokes the separate writer with the current turn, retrieved candidates and the bounded non-declarative set. Validated create/update/delete plans cite actual conversation sequence numbers; user-stated entries may cite only user messages, and assistant-derived entries remain model inferences. User introductions remain attributed claims; explicit teaching of durable habits or persona may become non-declarative memory. The plan and turn deduplication marker commit together. The built-in first greeting is not user evidence.

`maxImplicitMemories`, `memoryChars`, `maxChanges`, `inputChars`, `outputChars`, `maxTokens` and `timeoutMs` bound auxiliary work. Invalid references, oversized or truncated output and incompatible vectors refuse updates. A memory failure leaves the completed chat reply successful and shows a separate warning beside the conversation; the user may continue. Chat and Knowledge Base report the failed stage and safe error code/message, including HTTP status, provider completion reason or validation field. Retry preserves its own error, including replaced or unavailable turn evidence. Memories and Knowledge Base also show the reviewed turn and completion time, with the update probability and captured threshold for Jev decisions, including no-update outcomes. These diagnostics describe the latest review in the running process and are not restored after restart; credentials, conversation text and raw provider error bodies are excluded. Retry can reuse the latest failed turn while its live evidence remains available, without generating another chat reply. A newer turn or restart requires fresh conversation evidence. No completed review marker is written on failure; storage or backup errors can still follow a committed update and require inspection before retry. Cancellation is checked before commit admission; admitted primary writes drain.

Registered auxiliary calls use `memory.reasoningEffort: auto` by default: select `off` when the captured model advertises it, otherwise retain its default. This applies to memory decisions, writing, consolidation and emotion inference; chat settings are independent. Use `provider-default` to inherit provider behavior or an exact advertised effort such as `low`; unsupported explicit values fail before dispatch. Jev and dedicated HTTP routes retain their own protocol settings. `memory.maxTokens` (default 4096) covers reasoning and final output according to the provider. A `max-tokens` failure reports the effective effort and refuses even parseable JSON; lower auxiliary reasoning or increase the token budget. After restarting with corrected configuration, use Consolidate now in Memories to retry retained pending evidence.

## Experiences, previous interpretations and association

A positive decision may produce an `experience` alongside the writer’s `changes`. Its summary, topics, confidence and cited sequence numbers describe a meaningful exchange; the Host derives conversation identity and event times from those citations. A remembered experience is a declarative episodic candidate with `MemoryExperience` metadata (`sessionId`, `startedAt`, `endedAt`, `topics`). The writer may extend a supplied recent experience from the same conversation when the exchange continues it. `memory.experienceWindowMs` defaults to 1,800,000 milliseconds. An unrelated or unavailable experience ID refuses the whole plan. The experience, derived memories, `experienceIds` links and review marker commit together, subject to `maxChanges`. Legacy changes-only writer responses remain valid. Old conversations are not automatically converted into experiences.

Model-generated content, category, layer, importance, confidence or attribution changes retain the earlier interpretation in `history` as a `MemoryRevision`, with its original sources, `recordedAt` and `supersededAt`. These timestamps describe the system’s recorded understanding, not objective truth or a claim’s real-world validity interval. Vector rebuilding and recall do not increase confidence or create versions. History contributes to storage limits. Explicit deletion removes the record’s content and versions and clears references to a deleted experience; source Session messages and audit events remain.

Before each accepted actual user input, bounded association searches related memories without an additional LLM call. It embeds at most `memory.associationInputChars` characters (default 1,000, also bounded by `inputChars`), then selects at most `associationLimit` cues (default 3) within the complete `associationChars` JSON budget (default 2,000). Set `associationLimit: 0` to disable it. Cues carry current text, attribution, confidence, prior-version count and experience metadata; `genesis_recall` provides detailed sources and versions. Both cues and explicit tool results are logged in their receiving Session. Retrieved experiences can bring their associated knowledge into the same bounded result. Lexical matches may retrieve an old wording while the result clearly retains the current interpretation and its history. A lookup failure supplies an explicit unavailable cue and a safe Host diagnostic; it does not mean memory is absent, and chat can continue.

Settings → Memories shows experience times, linked experience IDs and expandable previous interpretations. Text search covers current content, history, topics and exact memory IDs. Non-declarative entries remain attributed prompt guidance; forgetting is not implemented.

## Automatic habits and idle consolidation

With `memory` enabled, new reviewed memories queue one durable maintenance revision. After all live Agents have been idle for `memory.consolidation.idleMs` (default 60,000 ms), one pass uses the saved writer and embeddings. The worker considers at most `batchLimit` recent complete records (default 20) within half of `inputChars`, leaving room for the request wrapper and feedback groups; older records remain available to recall. It preserves source experiences and operator-authored records, derives attributed interpretations, and versions accepted updates. It never generates a chat reply or wakes the character for an external task. The original conversation logs exact auxiliary inputs and responses. After restart, pending work resumes its source Session only for this audit and disposes that privately owned Agent afterward; missing or unreadable source persistence fails visibly.

A learned `MemoryHabit` contains a context cue, conditional response, active flag and actual user-event references. Formation requires `minHabitSupport` independent completed user turns (default 3) supporting the same behavior. Repeated assistant statements, repeated manual saves of one turn and historical records without completed-turn evidence do not count. Explicit user teaching may still enter non-declarative memory during ordinary review. Inferred habits are procedural, non-declarative model inferences; current corrections can retire them, and no habit grants tool authorization. Inactive habits are excluded from prompt guidance but remain searchable with history. Editing takes over the current content and clears automatic habit metadata; converting a habit to declarative memory removes its behavioral influence and prevents consolidation from reactivating that record. Editing, deleting or converting a learned habit also marks its prior user support as overridden, so automatic learning requires fresh supporting exchanges rather than immediately recreating it from the same evidence.

Settings → Memories provides an automatic-consolidation toggle, immediate pass and last-result/error details. The toggle persists across modes and restarts; disabling retains pending evidence and still allows an explicit pass. Automatic work defaults to enabled, has a `cooldownMs` of 300,000 ms between successes and a `retryMs` of 60,000 ms between failures, and stops after `maxFailures` (default 3) for a pending revision. Fresh evidence or an explicit pass resets that revision’s retry budget. A successful or empty pass consumes its revision without queuing itself again. User activity cancels inference and retains pending work; deadline failures consume retry budget. Timer disposal aborts and drains the writer and any privately resumed Agent before storage closes. Displayed settings errors retain safe stage/code/message details after restart; refresh Memories to sample background progress.

The commit checks the work revision and every supplied memory version; concurrent edits or deletions discard the stale plan. Original sources remain unchanged. These are bounded heuristic learning and summarization operations, not proof of human memory, subjective experience, or a general autonomous scheduler. They add at most one writer call and `maxChanges` embedding calls per pass, under the existing inference, prompt and storage budgets; no independent model role is required.

## Selected memory organization

In Settings → Memories, select two or more memories or past experiences and choose Organize selected memories. Choose the result count automatically or enter an exact count, bounded by the selection size and `memory.maxChanges`. The saved writer sees compact `m1`, `m2` source handles bound by the Host to the displayed memory versions; life-event IDs are not valid selection references. It integrates only those versions; this action bypasses the decision model and idle scheduler. Source selection is bounded by `memory.organizationLimit` and half `memory.inputChars`; oversized selections are refused in full. Each result must cite selected memories, every selected memory must be covered, and confidence cannot exceed the strongest cited source. Results are declarative model inferences with embeddings, not new verified facts or automatically learned habits.

All results and deletion of the selected old records commit atomically with a `memory.organized` life event. Original life-event evidence remains; links to deleted experiences are removed from surviving memories. That event records the selected versions and result-to-source mapping. A separate durable maintenance Session logs exact auxiliary inputs and outputs without generating chat messages. Requests retain a branded `MemoryOrganizationId` across retries; a committed request returns the same results after restart. Changed or deleted sources, invalid evidence, embedding errors, cancellation before commit or malformed output retain the old memories and publish no partial results. Failed UI operations retain the selection and result count; refresh and select current versions after conflicts. No automatic selected-memory organization runs.

## Manual memory controls

Settings → Memories is separate from Knowledge Base configuration. It lists bounded previews, searches stored text and supports creating, editing and deleting candidates, plus conversion between declarative and non-declarative layers. `MemoryKind` names those two layers; `MemoryDraft` contains content, category, layer, importance and confidence. Direct entries require no model or embedding call. New entries receive an operator attribution and hashed source event. Editing directly replaces current fields, retains source references and any already existing history, and invalidates changed text’s vector for lazy rebuilding; it adds neither an edit event nor a historical version. Conversion preserves content, identity, sources and compatible vectors without adding history. Manual deletion also adds no edit event. A bounded current-state evidence exclusion keeps manually retired habits from being relearned from the same old evidence. Non-declarative count and prompt-size budgets apply to both edits and conversions.

Each completed assistant reply offers Memory → choose layer → Generate and save. Automatic review remains enabled. This explicit request bypasses the decision model, retrieves related candidates and asks the independent writer to extract sourced changes in the chosen layer; it cannot delete memories. No eligible durable information returns a visible no-change result. A private replayable projection locates the selected reply and its actual user input, including after another turn or restart of the same conversation; the built-in greeting alone is excluded. Model inputs and responses use the existing logged auxiliary records. Repeating the same committed reply/layer request does not call the writer or save twice.

Direct creation retains a client UUID across failed retries. Edits, conversions and deletions check the displayed `updatedAt`; a concurrent change is refused visibly before commit. Refresh before editing the latest version. Failed operations retain drafts or rows and display the concrete diagnostic. Deletion removes the current memory and its backup copy, while source Session messages and append-only audit events remain; it does not erase the original conversation. Storage/backup failures may follow a primary commit and require inspection before retrying.

## Persistence and local backup

The existing life storage shares identity, persona memory and long-term memory across Sessions without merging their contexts. Memory records keep source-event references, kind, attribution and optional embedding caches. Endpoint, model and dimensions identify each embedding space. New and updated vectors persist; historical or incompatible caches are rebuilt lazily during search. Search currently scans a bounded local vector collection, rather than an external vector database.

Every primary commit also writes an owner-private independent backup. `backupPath` overrides the default `${leasePath}.backup.json`; this file is a commit manifest whose components live in the sibling `${backupPath}.d/` directory. Components use temporary files, file synchronization and atomic replacement before manifest publication. Deleting a memory removes its obsolete text, versions and vector components from primary storage and the backup after successful commit. Include the manifest, its entire component directory and both primary domains in recovery copies. See [storage layout](data-model.md#life-storage).

A backup failure can occur after the primary commit. Genesis stops dependent state operations and reports the uncertain result; inspect both copies before restart. If primary state is absent while a backup exists, Genesis refuses to create a replacement life. Stop writers and preserve both copies. The [backup reader](../../packages/experimental/genesis/src/backup.ts) accepts legacy snapshots and split backups, verifies referenced hashes and validates the reconstructed life with `stateSchema`. Restore that validated complete life as a legacy `states/life` record through the configured Storage Domain backend; the next startup publishes split components. A backup manifest alone cannot replace `genesis.json`; its sibling directory is required. Unknown or corrupt primary state is never silently replaced.

## Verification and limits

The keyless Loader integration exercises separate model roles, semantic synonym retrieval, restart continuity, Session isolation, local backups and rejected evidence/vector responses. Live provider calls require deployment credentials and have not been exercised by these fixtures. Split storage retains the existing capacity limits and loads the full bounded life at startup; memory inferences are not verified facts. For persistent tool learning and the first-start account/naming flow, see [first awakening](awakening.md). Independent [emotion appraisal](emotion.md) can reuse these model routes; autonomous wake scheduling remains unimplemented.
